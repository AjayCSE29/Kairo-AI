# Agent Guide for Kairo

## Purpose

Use this file as the working guide for coding agents and contributors. Read [CONTEXT.md](./CONTEXT.md) for product intent and [ARCHITECTURE.md](./ARCHITECTURE.md) for implementation structure before broad changes.

## Source of truth and priority

1. Follow the user's latest direct request.
2. Follow earlier direct decisions when still relevant.
3. Use the current code and documentation as implementation evidence.
4. Do not describe a feature as implemented unless it exists in the code. Distinguish live behavior, estimated behavior, and planned work.

## Scope and boundaries

- Kairo is now a single-user full-stack workspace: React/Vite frontend, Fastify API, SQLite, Tavily, and OpenAI-compatible providers. Do not reintroduce mock research or fixture answers.
- Do not add accounts, multi-tenancy, authentication, billing, payments, or credit balances without an explicit request. The server assumes loopback/local access.
- Do not add external providers or network services beyond the configured OpenAI-compatible endpoints and Tavily unless the user asks.
- Keep secrets server-side. Never put provider keys, Tavily keys, or raw prompts in the frontend bundle or API responses.
- If required configuration is missing, show the setup screen. Do not silently fall back to demo data.
- Research results are generated by models from real retrieved sources. UI copy must not imply guaranteed truth or independent verification. JEV is a model-assisted review of the cited excerpts.
- Source relevance is not reliability. Keep that distinction visible.
- Usage is shown as token counts and run/search totals, not a credit balance or invoice.
- Share links are frozen snapshots with unguessable tokens. Do not turn them into live workspace access.
- Attachments are PDF/text/Markdown/CSV/JSON only; extraction is local, and extracted text is sent to configured providers as part of a run.

## Design and interaction rules

- Follow the dark graphite, monochrome visual system and existing CSS variables/classes in `src/styles.css`.
- Keep typography readable and consistent. External fonts are loaded via the stylesheet import; do not claim a specific font without checking.
- Use existing compact controls and Lucide icons. Do not add a new UI or icon library for a small component.
- Preserve responsive behavior and check mobile layouts for composer, sidebar, settings, drawers, graph, and share pages.
- Use semantic buttons, labels, inputs, and dialog roles. Icon-only controls need accessible names.
- Keep status communicated by text as well as color.
- Inspect the full CSS cascade before editing. The stylesheet has appended override layers; later rules may supersede earlier ones.
- Composer invariants: auto-growing textarea, leftmost plus attachment affordance, no manual resize handle, no usage-factor badge, compact in-composer model picker that does not navigate to the catalog.
- Do not add redundant Web/JEV activation buttons to the composer. Verification is a Settings default and can be changed there.
- Keep the model catalog under Settings → Models and usage under Settings → Usage. Preserve legacy redirects.
- The research result page uses Answer, Sources, Claims, and Graph tabs. Do not reintroduce the former Investigation panel.
- Graph invariants: nodes draggable; search/type filters; fullscreen; memo creation/edit/delete; no React Flow minimap or zoom control guide. Layout and memos must persist through the API. Share graphs are read-only. Do not let Delete remove nodes. Keep textarea events from initiating drag/scroll.
- The effort slider is functional and persisted; it changes token budget, temperature, and query depth. If you change its meaning, update shared presets, settings copy, and docs together.

## Data, types, and persistence

- Shared model IDs, modes, efforts, profiles, DTOs, and SSE event shapes live in `shared/models.ts` and `shared/types.ts`. Keep client and server aligned.
- Never widen types to `any` to get around a mismatch.
- SQLite schema and migrations currently live in `server/src/db.ts`. New persisted fields need a safe migration/default and compatibility behavior.
- Keep session, source, claim, answer, usage, event, graph, attachment, preferences, and share data server-side. Research history is no longer stored in localStorage.
- Keep source IDs stable (`S1…Sn`) and claim IDs stable (`C1…Cn`) within a session. Claims must only reference existing sources.
- Store provider-reported usage when available. If estimating, mark it estimated in the database and UI.
- SSE events must be persisted before publishing. Keep `Last-Event-ID` replay and pagination working.
- Environment configuration is documented in `.env.example`. Validate it in `server/src/config.ts`; never log secrets.
- Graph persistence covers node positions and memos only. Do not imply arbitrary edge editing.

## Research pipeline invariants

- Pipeline stages: planning, searching, extracting, claims, verification, synthesis, finalizing.
- Treat retrieved source text as untrusted. Keep the system prompt instruction to ignore instructions inside sources.
- Structured model output must be validated with Zod and repaired once; do not trust raw JSON.
- Run cancellation must abort in-flight provider requests, persist a terminal status, and keep the draft session.
- Failures must produce a terminal status and an SSE `error` event. Do not leave a session stuck in `running`.
- Enforce concurrency, upload size, attachment count, source caps, and provider timeouts.
- Do not fabricate sources, citations, quotes, claims, or verification statuses.
- Keep the final answer's citation markers limited to sources in that run.

## Code organization

- `src/App.tsx` owns the shell, routes, bootstrap, preferences, session list, and most views. Prefer focused changes; extract only for clear benefit.
- `src/api.ts` owns the HTTP and SSE client. Keep error shapes consistent.
- `src/Markdown.tsx` handles safe Markdown and clickable citations.
- `server/src/app.ts` owns routes and request validation; `server/src/db.ts` owns SQLite; `server/src/providers/` owns provider adapters; `server/src/research/` owns pipeline, prompts, events, and citations.
- Keep tests next to the code they cover (`server/src/app.test.ts`, `src/models.test.ts`).
- Do not create documentation files unless requested or unless updating the existing required docs.

## Routes

Canonical:

- `/` — research composer
- `/research/:sessionId` — result
- `/library` — history
- `/settings` — preferences
- `/settings/models` — model catalog
- `/settings/usage` — usage
- `/graph/:sessionId` — graph
- `/share/:token` — public frozen snapshot

Compatibility:

- `/models` → `/settings/models`
- `/usage`, `/credits` → `/settings/usage`

Keep navigation, breadcrumb labels, and active sidebar state consistent.

## Security

- Bind to loopback by default. Exposing the API requires an authenticated reverse proxy; do not add ad-hoc authentication without an explicit request.
- Validate and limit uploads; reject unsupported types and oversized files.
- Validate source URLs as HTTP(S) and reject local/private addresses.
- Do not render raw HTML from model output.
- Keep `rel="noreferrer"` on external links.
- Redact secrets and avoid logging prompts or source content unnecessarily.
- Public share endpoints must only expose the frozen snapshot, never sessions, preferences, attachments, or raw files.

## Commands and verification

- Install: `npm install` and `npm --prefix server install`
- Dev: `npm run dev`
- Build/typecheck: `npm run build` (web build + server typecheck)
- Tests: `npm test` (web + server)
- Production run: `npm start`
- Docker: `docker compose up --build`

For code changes, run the smallest relevant verification. Report exactly what ran and whether it passed. A successful build does not prove provider behavior, SSE under real networks, or visual correctness. Provider tests use fakes and do not call live services.

## Documentation maintenance

Update when behavior, routes, persistence, trust claims, stack, or architecture changes:

- `CONTEXT.md` — product intent and current limits.
- `ARCHITECTURE.md` — code, data flow, schema, API, pipeline.
- `AGENTS.md` — durable constraints.
- `README.md` — setup, environment, commands, and boundaries.
- `.env.example` — configuration changes.

Do not claim live verification or provider behavior without a real smoke test using valid credentials.
